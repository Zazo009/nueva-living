# Nueva Living — Multilingual System

This document describes the internationalization (i18n) architecture as it
exists today: how it works, how to extend it, what is fully translated, and
the small set of known gaps. The system is built so partial translation is
always safe and honest — a missing translation leaves English text in place,
never a blank or broken page.

## Why this architecture, not a JS framework

The site is a static HTML generator: six Node scripts run in sequence (see
`netlify.toml`):

1. `build_footer_pages.mjs` — about/contact/legal/guides/areas/area-* pages
2. `build_property_pages.mjs` — 13 property pages + generated card grids
3. `build_segment_pages.mjs` — new-build-apartments-penthouses-* + guides.html
4. `build_homepage_locales.mjs` — clones `nueva-living-home.html` per locale
5. `build_developments_locales.mjs` — clones `developments.html` per locale
6. `build_dist.mjs` — final packaging into `dist/` (SEO, GTM, newsletter,
   shortlist, system styles, sitemap)

Translation happens **at build time**, producing a separate, fully-formed
static page per locale. No client-side language switch, no hydration, no
flash-of-wrong-language.

## Supported locales

Defined centrally in `content/i18n/locales.json`:

| Code | Language | Direction | URL prefix |
|---|---|---|---|
| `en` | English (default/fallback) | ltr | *(none — site root)* |
| `es` | Spanish | ltr | `/es/` |
| `fr` | French | ltr | `/fr/` |
| `de` | German | ltr | `/de/` |
| `ru` | Russian | ltr | `/ru/` |
| `ar` | Arabic | **rtl** | `/ar/` |

English keeps every existing URL unchanged. Every other locale gets a
parallel directory tree (`es/developments.html`, `ar/index.html`, …) using a
`<base href="../">` tag so all relative asset paths resolve unchanged.

## The four translation mechanisms

### 1. `t(key, locale, vars)` — shared UI strings

`scripts/lib/i18n.mjs` + `content/i18n/strings.json` (~250 keys). Used for
nav/footer/breadcrumb chrome, form labels, FAQ content, availability tables,
cinematic-viewer chrome, and anything rendered by a locale-aware function.
Falls back to English, warns on missing keys outside production.

**Gotcha (this bit the project three separate times):** a function full of
`t()` calls is only locale-aware if its call site actually passes `locale`.
Content baked into a template literal evaluated once at module load renders
English forever, no matter how localized the function looks. When adding
content, check where the render function is *called*.

### 2. `localizeProject(object, locale)` — structured content overlays

Merges `object.i18n.<locale>` onto the English source, one level deep.
Used for `content/liora-projects/*/project.json` (all 13 projects have full
es/fr/de/ru/ar overlays) and `content/nueva-areas.json` (all 5 areas).
Translators override prose fields; factual/structural data (prices, units,
hrefs, image sizes) is never restated and never drifts.

### 3. Literal find/replace entry tables — opaque page bodies

For hand-authored or once-rendered HTML where content isn't structured
fields. Entry shape: `{ find: 'English text', es: '…', fr: '…', … }`,
applied post-render with `.split(find).join(replace)`.

- `scripts/lib/footer_page_translations*.mjs` → footer pages (4 group files)
- `scripts/lib/segment_page_translations.mjs` → segment pages + amenity list
- `scripts/lib/developments_page_translations.mjs` → developments page
  (also exports `PROJECT_CARD_ENTRIES` + `TAG_LABELS`, shared with segment
  pages for generated project cards)
- `HOMEPAGE_CONTENT_ENTRIES` in `build_homepage_locales.mjs` → homepage

**Rules learned the hard way:**
- Entries are applied **longest-find-first** everywhere. A short entry
  ("Areas" → "Zonas") firing inside a longer string ("Areas We Cover")
  corrupts it before its own entry can match. Never rely on file order.
- Scope short finds with surrounding markup (`aria-current="page">Areas</span>`,
  `<option>…</option>`, `<li>…</li>`) instead of bare words.
- `data-filter` attribute values and other JS matching keys stay English;
  only visible label text between `>` and `<` is translated.

### 4. Runtime `data-i18n-*` attributes — client-side JS strings

`assets/liora/liora-discovery.js` (developments filters) reads its runtime
strings (result counts, "Any price", AI-search status) from `data-i18n-*`
attributes on the `[data-discovery]` section, written per-locale by
`build_developments_locales.mjs`. English pages carry no attributes and use
the built-in literals. Selected-filter chips display the pill's translated
`textContent`, keyed by the English `data-filter` value.

## RTL (Arabic)

- `assets/liora/liora-rtl.css` — flips physical offsets the logical-property
  defaults don't cover (switcher panel, shortlist trigger margins).
- Self-hosted Arabic font in `assets/fonts/arabic/`.
- `<html lang="ar" dir="rtl">` set per page; layout mirrors via flexbox.
- **Never hide elements with `left: -9999px`** — on RTL documents that
  *expands* the scrollable area 10,000px leftward (this happened with the
  newsletter honeypot; use `clip-path: inset(50%)` hiding instead).

## Language switcher

Rendered server-side on every page (`renderLanguageSwitcher()` in
`i18n.mjs`; the homepage has its own copy in `build_homepage_locales.mjs`).
A native `<details>` dropdown; options use **absolute** hrefs
(`/es/developments.html`) because Netlify's link rewriting doesn't understand
`<base href>`. Styled once, site-wide, in `assets/liora/nueva-system.css`
(`.lang-switcher*` rules) — injected on every page by `build_dist.mjs`.

## SEO

- Reciprocal `hreflang` link tags on every page, plus `x-default` → English.
- Per-locale `<title>`, meta description, canonical, `og:url`, `og:locale`.
- `dist/sitemap.xml` lists every locale variant (~192 URLs) with reciprocal
  `xhtml:link` alternates, driven by what actually exists on disk.

## Coverage today

Fully translated in all 5 non-English locales: homepage (including the
cinematic viewer's per-project data), all 13 property pages, developments,
all footer/legal/guide pages, 5 area pages, 3 segment pages, contact/area
forms, amenity lists, shared FAQ, newsletter block, discovery filters, and
the guide checklist.

**Known gaps (deliberate, not accidental):**
1. Per-photo media captions/alt text (`media.items[].caption/alt`) — English
   for 12 of 13 projects (~150 items). Largest remaining content chunk.
2. `compare.html`, `thank-you.html`, `404.html` — English only, no locale
   variants, excluded from the locale loops in `build_dist.mjs`.

## Adding a new locale

1. Add it to `content/i18n/locales.json`.
2. Add its column to every key in `content/i18n/strings.json`.
3. Add `i18n.<code>` overlays to each `project.json` and `nueva-areas.json`.
4. Add its column to every find/replace entry table.
5. If RTL, extend `liora-rtl.css` checks.
6. Run the build; anything missed simply stays English.

## Verifying coverage

The audit approach that caught every real bug: build, then scan each locale
page's visible text (`>text<` between tags, scripts/styles stripped) for
English stop-words, excluding proper nouns. Check both directions: entries
whose `find` no longer matches (corruption/drift) *and* source strings with
no entry at all. Also verify English pages contain no leaked translations.
