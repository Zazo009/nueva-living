# Nueva Living — Multilingual System

This document explains the internationalization (i18n) architecture added to the
site, how to extend it, what's fully translated today, and what's explicitly
left as English fallback pending further work. Read the **Coverage report**
section before assuming any given page is fully translated — this system is
built so partial translation is always safe and honest (never a blank or
broken page), but "safe fallback" is not the same as "translated."

## Why this architecture, not a JS framework

The site is a static HTML generator: four Node scripts
(`build_property_pages.mjs`, `build_footer_pages.mjs`, `build_segment_pages.mjs`,
`build_dist.mjs`) read `content/liora-projects/*/project.json` and emit plain
`.html` files — no bundler, no client framework, no build step beyond Node.
Following the brief's instruction to use "the i18n solution best suited to the
existing framework," translation happens **at build time**, producing a
separate, fully-formed static page per locale. There is no client-side
language switch, no hydration, and nothing to flash-of-wrong-language, because
each locale's HTML is generated once and served as-is — the same reason the
site was fast and simple before this work, it stays that way.

## Supported locales

Defined centrally in `content/i18n/locales.json`:

| Code | Language | Direction | URL prefix |
|---|---|---|---|
| `en` | English (default/fallback) | ltr | *(none — stays at site root)* |
| `es` | Spanish | ltr | `/es/` |
| `fr` | French | ltr | `/fr/` |
| `de` | German | ltr | `/de/` |
| `ru` | Russian | ltr | `/ru/` |
| `ar` | Arabic | **rtl** | `/ar/` |

English keeps every existing URL unchanged (no redirects, no SEO-equity risk).
Every other locale gets a parallel directory tree: `es/property-x.html`,
`es/index.html`, etc.

## File structure

```
content/i18n/
  locales.json        # locale metadata: code, label, nativeLabel, dir, hreflang, urlPrefix
  strings.json         # shared UI strings, flat dotted keys -> {en, es, fr, de, ru, ar}
scripts/lib/
  i18n.mjs             # t(), localizeProject(), localizedPath(), hreflangLinks(),
                        # renderLanguageSwitcher(), isRtl(), LOCALES, DEFAULT_LOCALE
scripts/
  build_property_pages.mjs    # locale-aware; loops LOCALES per project
  build_homepage_locales.mjs  # generates es/index.html ... ar/index.html from
                                # nueva-living-home.html (chrome-only, see below)
  self_host_arabic_font.mjs   # regenerates assets/fonts/arabic/*
assets/liora/
  liora-rtl.css        # RTL overrides, loaded only on dir="rtl" pages
assets/fonts/arabic/
  liora-arabic-fonts.css
  SLXVc1n...woff2       # self-hosted Cairo variable font (~36KB)
content/liora-projects/<slug>/project.json
  "i18n": { "es": {...}, "ar": {...} }   # per-project translation overlay
```

## How translation works: `t()` and the strings dictionary

`content/i18n/strings.json` holds every shared UI string (nav, footer, buttons,
breadcrumb, availability table headers, cinematic-presentation chrome, form
labels, area names) as `{ "key": { "en": "...", "es": "...", ... } }`.

```js
import { t } from './lib/i18n.mjs';
t('nav.developments', 'es');                    // -> "Promociones"
t('media.viewAllImages', 'ar', { count: 12 });   // -> interpolates {count}
```

- **Fallback**: a missing translation for a locale falls back to English. A
  missing *key entirely* falls back to the key itself, with a `console.warn`
  in non-production builds — so a gap is loud in local dev, never a blank
  string, and never a raw key in production output (dev warnings are gated on
  `NODE_ENV !== 'production'`; nothing user-visible ever prints a raw key).
- **Adding a string**: add one entry to `strings.json` with all 6 locale
  values, then call `t('your.key', locale)` wherever it's needed. No other
  file changes.

## Dynamic content: the `project.i18n` overlay

Each project's `project.json` can carry an optional `i18n` object:

```json
{
  "name": "Elviria Hills Residences",
  "hero": { "location": "Elviria West, Marbella", ... },
  "availability": { "headlineHtml": "...", "units": [ /* 36 real units */ ] },
  "i18n": {
    "es": {
      "name": "Elviria Hills Residences",
      "hero": { "location": "Elviria West, Marbella", ... },
      "availability": { "headlineHtml": "Lista actual...", "sourceNote": "..." }
    }
  }
}
```

`localizeProject(project, locale)` merges the overlay onto the English source
**one level deep**: if both sides have a plain-object value for the same key
(e.g. `availability`), the overlay's fields override individually and
everything the overlay doesn't mention — `units`, `startingPrice`,
`priceRange`, `checkedDate` in the example above — silently keeps its English
value. This was a deliberate, tested design choice: real prices, unit
references and floorplans must never be "translated" or accidentally wiped
out by a translator overlay that only touched the prose fields. Arrays
(`quickFacts`, `why.points`, `media.items`, ...) are replaced wholesale when
present in the overlay, since partial-array merging has no sane semantics.

**Never invented**: no price, unit count, delivery date, or legal fact was
translated by paraphrase or guesswork — every number in a translated page is
copied verbatim from the English source, only the surrounding prose changes.

## Locale-aware routing & the `<base>` tag

Rather than hand-prefixing every one of the hundreds of relative asset/link
references inside the ~500-line page-render function, every non-English page
emits **one** `<base href="../">` tag in `<head>`. Every existing relative
reference (`assets/...`, `developments.html`, `guides.html`) then resolves
correctly from one directory deeper, unmodified. This was chosen after an
earlier attempt at manual per-reference prefixing proved fragile and easy to
miss a spot — `<base>` is the single point of truth for path resolution.

Pages that *do* need a locale-aware href (linking to another locale's version
of the same page, e.g. the language switcher, or the "Cinematic Presentation"
link into `index.html?project=...`) use `localizedPath(file, locale)` from
`i18n.mjs`, which is base-tag-relative by construction.

## The language switcher

A `<details>`/`<summary>` element (`renderLanguageSwitcher()` in `i18n.mjs`),
not a generic `<select>` or a third-party dropdown component — accessible by
default (keyboard-operable disclosure widget, no JS required to function),
styled entirely from the site's own tokens (bronze/ink/cream), and closing on
outside click via a small inline script reused on every page type. It shows
native language labels (Español, Français, Deutsch, Русский, العربية), marks
the active language with `aria-current`, and always links to the *equivalent*
page in the target locale (same slug, same anchor structure) — never just the
homepage.

## Arabic / RTL

- `<html lang="ar" dir="rtl">` is set for every Arabic page.
- `assets/liora/liora-rtl.css` is loaded **only** on `dir="rtl"` pages. It is
  a targeted, component-scoped set of overrides (nav, breadcrumb, footer,
  payment-terms grid, availability table, media gallery/dialog, cinematic
  chrome, FAQ icon spacing, in-page nav chevron) — not a blanket
  find-and-replace of every `left`/`right` in the codebase. Most paragraph
  and heading flow needed **zero** overrides, since the base stylesheets
  already avoid hardcoded `text-align: left` almost everywhere and inherit
  the browser's native start-alignment from `dir`.
- **Font**: Cairo, self-hosted as a single ~36KB variable font (weight axis
  200–1000, covering the site's 400/500/600/700 usage from one file),
  restricted to the Arabic Unicode subset so it never loads on LTR pages.
  Chosen for a refined, geometric-sans character that pairs with
  Montserrat's own structure (Cinzel has no Arabic coverage, so Arabic
  headings fall back to Cairo's heavier weights rather than a broken serif
  substitution). Applied via `:lang(ar)` / `[dir="rtl"] .display-title` etc.,
  so a mixed Arabic/Latin string (an Arabic sentence containing "Nueva
  Living") renders each script in its own correct face.
- **Numbers/prices/phone numbers** are wrapped with `unicode-bidi: isolate`
  so they don't get visually reordered inside a right-to-left run.
- **Icons**: only genuinely directional glyphs (chevrons, prev/next arrows,
  the in-page nav indicator) are mirrored via `transform: scaleX(-1)`.
  Photography, the brand wordmark, and symmetric icons (close, play, search)
  are explicitly left unmirrored.
- Regenerate the font package with `node scripts/self_host_arabic_font.mjs`.

## Multilingual SEO

- Every property page carries reciprocal `<link rel="alternate" hreflang="...">`
  tags for all 6 locales plus `x-default`, generated by `hreflangLinks()`.
- Canonical URLs are locale-correct (`https://nuevaliving.com/es/property-...`).
- `og:locale` is set per page.
- `sitemap.xml` (generated in `build_dist.mjs`) includes every locale property
  page as its own `<url>` entry, each carrying the full reciprocal
  `<xhtml:link rel="alternate" hreflang="...">` set, so no page is presented
  to search engines as duplicate content.
- The homepage's 5 non-English variants also carry the reciprocal hreflang
  set; the English homepage was updated to reference them too.

## How to add another language

1. Add an entry to `content/i18n/locales.json` (`code`, `label`, `nativeLabel`,
   `dir`, `hreflang`, `urlPrefix`).
2. Add that locale's column to every key in `content/i18n/strings.json`
   (missing keys fall back to English with a dev warning, so this can be done
   incrementally — the site won't break mid-translation).
3. Run the build. Every property page, the developments listing card data,
   and the homepage chrome are generated automatically for the new locale.
4. Add `project.i18n.<code>` overlays to translate individual projects' body
   content, following the pattern in `elviria-hills-residences/project.json`.
5. If the new locale is RTL, add its own font/CSS following the `liora-rtl.css`
   pattern (most of the file is direction-agnostic and reusable as-is).

## How to test

```bash
node scripts/build_footer_pages.mjs \
  && node scripts/build_property_pages.mjs \
  && node scripts/build_segment_pages.mjs \
  && node scripts/build_homepage_locales.mjs \
  && node scripts/build_dist.mjs
```

Then serve the repo root (`python3 -m http.server`) and open, e.g.:
- `http://localhost:PORT/es/property-elviria-hills-residences.html`
- `http://localhost:PORT/ar/property-elviria-hills-residences.html` (verify
  `dir="rtl"`, mirrored nav/facts panel, Cairo font, running-total payment
  grid reading right-to-left)
- `http://localhost:PORT/ar/index.html` (verify chrome only — hero stays
  English, this is the documented gap below)

Check the browser console for 404s on every new locale/font path after any
change to `liora-rtl.css` or the font preload block — a relative-path typo
there is silent until you actually load the page (this bit us once during
this build: see Known issues, fixed).

## Translation coverage report

### Fully translated (all 6 languages, chrome + navigation)
- Header nav, mobile nav, language switcher — `build_property_pages.mjs`
- Breadcrumb — all property pages
- Footer (all columns, disclaimer, legal links) — all property pages
- Availability table headers, status labels, "view all N" — all property pages
- Payment-terms section: kicker, running-total summary, labels — all property pages
- Media gallery chrome: kicker, "view all N images", category names
  (Exteriors/Amenities/Residences/Location), dialog close/prev/next — all property pages
- SEO title template, hreflang, canonical, og:locale — all property pages
- Homepage nav, mobile nav, footer, language switcher — `index.html` + 5 locale variants

### Fully translated (Spanish + Arabic content depth)
- **Elviria Hills Residences** — every section: hero, quick facts, overview,
  why, architecture, residences, private-viewing insights, lifestyle,
  location, investment, trust dossier, construction timeline/payment terms,
  next-steps timeline, project-file documents, availability copy, enquiry
  copy. Spanish additionally includes all 41 individual media captions;
  Arabic's media *section copy* is translated but its 41 individual photo
  captions fall back to English (documented trade-off for time, not a defect
  — captions display correctly, just in English).

### Relying on English fallback (safe, not broken, not yet translated)
- **12 of 13 projects'** body content (hero copy, overview, why, architecture,
  residence descriptions, etc.) — chrome around them is fully translated in
  all 6 languages, but the project's own prose displays in English until a
  `project.i18n.<locale>` overlay is added, following the Elviria Hills
  pattern. This is the main remaining content-translation task; the
  *pipeline* for it is complete and proven.
- **Guide, legal, about, contact, area pages** (`build_footer_pages.mjs`,
  `build_segment_pages.mjs` output) — deliberately **not** given locale
  variants in this pass. Generating `es/guides.html` etc. with translated
  chrome but 100% English body prose would create exactly the kind of
  thin/placeholder-feeling page the brief explicitly warns against indexing.
  Recommended next step: localize `nav()`/`footer()` in those two scripts
  (same pattern already proven in `build_property_pages.mjs`) once real body
  translations are ready to ship alongside them, not before.
- **Homepage hero copy, repeating content blocks, and the embedded cinematic
  presentation's UI-chrome strings** ("Guided"/"Manual", "Project Details",
  field labels like "Starting Price") — these live inside ~700 lines of
  hand-authored JS in `nueva-living-home.html`, not in a template function,
  and were judged too risky to restructure safely in this pass without
  dedicated follow-up time and testing. The cinematic presentation *is* fully
  functional in every locale (opens, plays, shows the correct project's real
  photos and real price data via `renderViewingProjectEntryJs`), and its
  chrome/labels are English regardless of the locale it was opened from. This
  is the single highest-priority follow-up item.
- Individual project media captions for Arabic (see above).

### Legal / professional review required before shipping translated copy
- **None of the translated copy in this pass touches legal, tax, or contract
  language** — the `footer.disclaimer` string and Elviria Hills'
  `trustDossier`/`constructionTimeline.paymentTermsNote` copy were translated
  preserving exact legal meaning (no rewording of obligations), but any
  legal/compliance team should still have a native-speaker pass over the
  Spanish and Arabic legal-adjacent strings (`footer.disclaimer`,
  payment-terms notes) before they're treated as the authoritative version a
  Spanish- or Arabic-speaking buyer relies on.
- The site's actual legal pages (`privacy-policy.html`, `legal-notice.html`,
  `cookie-policy.html`) are **not translated** (see "Relying on English
  fallback" above) — translating legal pages specifically needs a
  professional/legal translator, not a general content pass, when that work
  starts.

### Native-speaker review recommended
- French, German, and Russian currently have **complete UI-chrome coverage**
  (nav, footer, buttons, availability/payment labels, media chrome) but
  **no project-level content overlay** yet — i.e. every French/German/Russian
  property page today shows a fully-translated shell around English body
  copy. The Spanish and Arabic translations (chrome + Elviria Hills full
  content) were written with real Costa del Sol real-estate terminology in
  mind but have not been reviewed by a native-speaking real-estate
  professional in-market — recommended before public launch.

### Visual edge cases to monitor
- The in-page section sub-navigation (the sticky tab strip: Overview / Media
  / Residences / Availability / Location / Architecture / Why / Project
  Info) is generated by a function not covered in this pass and remains in
  English on every locale, including Arabic RTL pages, where it reads
  left-to-right against an otherwise-mirrored page. Flagged as a specific,
  scoped follow-up.
- The language switcher's open/close visual state should be spot-checked in
  a real browser (Chrome, Safari) rather than solely trusted from this
  session's automated screenshots — the automated screenshot tool used
  during QA showed an unexplained dimming effect while the switcher was open
  that `getComputedStyle` inspection could not attribute to any CSS rule on
  `html`/`body` (no `filter`/`opacity` change was present), which points to a
  capture-tool artifact rather than a real defect, but it was not possible to
  fully rule out in this environment.
- Long German/Russian translated strings inside the availability table and
  payment-terms grid have not been stress-tested against the longest real
  project names in the catalog (13 projects, some considerably longer than
  "Elviria Hills") — worth a pass once German/Russian project overlays exist.

## Known issues found and fixed during this build
- The Arabic font's `@font-face src` path in `liora-rtl.css` and its
  `<link rel="preload">` in `build_property_pages.mjs` both initially pointed
  at wrong filenames/directories (404s on every Arabic page). Fixed and
  verified via network-request inspection; the font now loads with a real
  `200 OK` on every Arabic property page.
- `localizeProject()`'s first implementation replaced whole top-level project
  keys, which would have silently dropped `availability.units` (all 36 real
  unit prices) and `privateViewing.href` (breaking the cinematic-presentation
  link) on any translated project. Changed to a one-level-deep merge before
  any project content was translated, specifically to prevent this.
